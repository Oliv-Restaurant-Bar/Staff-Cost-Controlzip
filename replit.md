# Personalkostentracker
An internal reporting tool for revenue, personnel costs, schedules, and KPIs, supporting multiple restaurant tenants.

## Run & Operate
- **Run:** `npm run dev`
- **Build:** `npm run build`
- **Required Env Vars:** Supabase URL and Anon Key (see `src/integrations/supabase/client.ts`)

## Stack
- **Frameworks:** React, TypeScript, Shadcn UI, Tailwind CSS
- **Runtime:** Node.js (via Vite)
- **Database/ORM:** Supabase (Auth, Postgres DB, KV Store)
- **Date Handling:** `date-fns`
- **Charting:** `recharts`

## Architecture decisions
- **Multi-tenancy:** Implemented via ID prefixes (`b-` for Beaulieu) in Supabase `employees` and `app_settings` keys, avoiding a dedicated `restaurant_id` column for simplicity and backwards compatibility.
- **Data Persistence Strategy:** LocalStorage is used as the primary, fast data store, with Supabase `app_settings` serving as a secondary, persistent backup, especially for financial and budget data. A sync hook (`useSyncStore`) handles this.
- **Authorization:** A centralized `usePermissions` hook enforces role-based access control, defined in `src/hooks/usePermissions.ts`, for granular control over features and data visibility.
- **Onboarding Flow:** Supports both existing employees completing details via a tokenized link and new self-registrations creating `pending_review` employee records for admin approval.
- **Time-based Reporting:** A global "Stichtag" (cut-off date) filter (`StichtagContext`) allows historical reporting and period closing, impacting various financial views.

## Product
- **Dashboard:** Overview of KPIs, revenue, costs, pro-rata personnel costs.
- **Schedule Planning:** Plan and actual shift schedules.
- **Target/Actual Analysis:** Comparison of planned vs. actual performance.
- **Personnel Master Data:** Employee data management (admin only).
- **Reporting/Financial Module:** Comprehensive financial data including prior year comparisons (P&L, budget).
- **Fixed Personnel Costs:** Overview of monthly salaries including 13th month salary by department.
- **Multi-Tenant Support:** Manage data for multiple restaurants (Oliv, Beaulieu) with tenant-specific data isolation.
- **Role-Based Access:** Different user roles (admin, service_manager, kueche_manager) have varying data access and permissions.
- **Onboarding System:** Facilitates employee data collection and self-registration.
- **Guest Link System:** Allows admins to generate temporary, password-protected read-only links for sharing sessions.
- **Pattern Warnings:** Identifies operational risks in schedules (e.g., consecutive days, short recovery times).
- **Product Master Data:** Centralized database for food/beverage articles, WES (cost of goods sold) per product, and tracking.
- **WES Analysis:** Compares WES from recipes, suppliers, and accounting for cost control.
- **Reservations Import:** Imports Foratable reservation-tool CSV exports (admin only) with upload→preview→save wizard and per-file history; recognizes returning guests for guest/behavior analytics. Existing-guest reuse before creating a new profile matches **only by normalized phone → email (case-insensitive), tenant-scoped** — name is NOT used for matching (avoids merging different people who share a name). Name-only bookings (no phone/email) still de-duplicate via the `(restaurant_id, match_key)` upsert.
- **Gästeexport Import (CRM-Anreicherung):** Admin-only import (`/foratable-import?tab=gaeste`, also linked in the Import-Zentrale) that enriches existing guests' manual CRM profiles from a Foratable *guest-list* export. Matches each CSV row to an existing guest by normalized email→phone→name (ambiguous matches are reported as "nicht zugeordnet"), then fills ONLY empty CRM fields (VIP, Newsletter, Sperrliste, Geburtstag, Firma, Lieblingsplatz, Notizen) — already-maintained values are kept and divergences counted as conflicts. Preview shows matched/created/updated/conflicts/unassignable before committing. Reservations, visit counts and segments are never touched; CSV-only, no email/WhatsApp.
- **Gäste-CRM:** Admin-only guest list with search (name/email/phone), visit count, first/last visit, average visit interval, and auto-segmentation (VIP ≥20 / Stammgast 8–19 / Wiederkehrend 3–7 / Neukunde 1–2 / Inaktiv >90d / Ohne Besuch). The list also surfaces the **manual CRM profile**: VIP/Stammgast-manuell, Firmenkunde, Newsletter and Sperrliste show as badges next to each guest; eight Ja/Nein/Alle filters (VIP manuell, Stammgast manuell, Firmenkunde, Newsletter, Sperrliste, Allergien vorhanden, Geburtstag hinterlegt, CRM-Notiz vorhanden) plus sortable Firma- and Geburtstag-columns let admins slice by manual data. Manual data is shown read-only here and never changes the auto-computed segment. The per-guest detail page is a full CRM customer record (Kundenakte) with six sections: a weighted CRM-Score 0–100 (niedrig/mittel/hoch/VIP-Potenzial), Besuchsverhalten (incl. a simple visit-count-based Gast-Status: Neu/Wiederkehrend/Regelmässig/VIP — separate from the segment), Präferenzen (favorite area/weekday/month/time/party-size), Risiko (no-shows, cancellations, overdue, at-risk), Besuchstrend (last 90d vs prior 90d → steigend/stabil/rückläufig), and a filterable reservation history (Alle/Nur Besuche/Nur Storniert/Nur No-Show). A visit = a completed reservation. Optional `guest_statistics` SQL view exposes the same KPIs directly in Supabase. The detail page now has two tabs: **Übersicht** (the read-only analytics above) and **CRM** (editable manual profile, see below).
- **Gäste CRM-Profil (Bearbeitung):** Admin-only editable manual CRM record per guest on the detail page's **CRM** tab — status flags (VIP / Stammgast manuell, Firmenkunde, Newsletter, Sperrliste), Stammdaten (Geburtstag, Firma, Sprache), Präferenzen (Lieblingsplatz/-bereich/-wein/-gericht), Allergien & Unverträglichkeiten, and internal notes. Two buttons: **Speichern** saves all fields at once and **Änderungen verwerfen** resets the form to the last-saved state (no DB write); both are disabled while there are no unsaved edits. If no record exists yet the form starts empty and the first save creates the row (upsert). Manual VIP/Stammgast flags additionally show as badges in the guest header and in a read-only **CRM-Profil** summary on the Übersicht tab (VIP, Stammgast, Geburtstag, Firma, Allergien, Notizen), shown independently of the auto-computed segment. Manual data is kept strictly separate and never changes the auto-computed segment/score/campaigns. Read-only guest links (guest sessions) cannot edit. Stored in the dedicated `guest_crm_profiles` table; computed live metrics remain untouched.
- **CRM Auswertung:** Admin-only dashboard (`/gaeste/auswertung`) with three tabs. **Übersicht:** guest-overview KPI cards (total/active/inactive/new/repeat-rate/VIP/Stammgäste/ohne Besuch/No-Show-Risiko/Rückkehrpotenzial), future-reservation analysis (current & next month, next 30/60/90 days, plus open/unanswered shown separately), and a custom date-range filter (active vs. open reservations + persons). All future-reservation tiles and the custom-range result tiles are clickable and open a detailed list of the underlying reservations (date, time, guest, persons, status, room/area, contact). **Rückkehrpotenzial:** KPI cards for overdue guests, at-risk Stammgäste and at-risk VIP, plus a list of overdue guests (most-overdue first) linking to each guest's detail page. **Kampagnen:** 18 predefined campaign lists — the 11 behavioural ones (überfällige/gefährdete Stammgäste & VIP, inaktiv >90/>180 Tage, 2+ No-Shows, Wiederkehrende, Stammgäste, VIP, Neukunden letzte 30 Tage, ohne Besuch) plus 7 manual-CRM ones (VIP manuell, Stammgäste manuell, Firmenkunden, Newsletter, mit Allergien, mit Geburtstag, Sperrliste). Each shows count + description with "Anzeigen" (detail table: Name, E-Mail, Telefon, Segment, Besuche, letzter Besuch, Tage seit letztem, Ø Intervall, No Shows) and "CSV exportieren" (only the filtered list, UTF-8 with BOM, semicolon-separated, German headers, `crm-kampagne-<slug>.csv`; the CSV always includes 8 manual-CRM columns). Admin-only, CSV download only — no email/WhatsApp. Computed live in TS from existing reservation tables; no new migration.
- **Rückkehrpotenzial (gefährdete Stammgäste) — Gästeliste:** Flags regulars slipping away — `returnRiskRatio` = daysSinceLastVisit ÷ personal avgDaysBetweenVisits; `isAtReturnRisk` = ratio ≥ `RETURN_RISK_FACTOR` (2) AND visits ≥ `RETURN_RISK_MIN_VISITS` (3). Logic in `src/lib/reservation-crm.ts`; filter (`returnRisk`) + sort key (`returnRisk`) in `src/lib/guest-list-filters.ts`; KPI count `returnRiskGuests` in `src/lib/reservation-dashboard.ts`. Surfaced on `/gaeste` (filter dropdown, quick-filter chip, "Rückkehr-Risiko" column showing the overdue ratio) and as the `Rückkehrpotenzial` KPI card in the `/gaeste/auswertung` Übersicht tab. This 2.0×-factor metric is distinct from the Rückkehrpotenzial **tab's** 1.5×-factor `OVERDUE_INTERVAL_FACTOR` logic (`reservation-dashboard.ts`); both coexist. Independent of the static "Inaktiv (>90d)" segment so it catches guests early. Admin-only, computed live in TS, no migration.

## User preferences

### Datenintegrität — verbindliche Entwicklervorgabe
- **Umsatzdaten dürfen niemals per localStorage-Overwrite oder naivem Blob-Write gespeichert werden.**
- Jeder Schreibpfad für `dailyBudgets` / `beaulieu:dailyBudgets` muss `safeUpsertDailyBudgets()` verwenden.
- `safeUpsertDailyBudgets` liest immer zuerst den aktuellen Supabase-KV-Stand, mergt, schreibt zurück.
- Bei KV-Schreibfehler erscheint eine sichtbare Fehlermeldung — kein stilles Fallback auf localStorage.
- Die `daily_revenues`-Tabelle (Roadmap in diesem File) wird erst aktiviert, wenn die aktuelle Lösung fachlich fertig getestet ist. Bis dahin keine Migration ausführen.

## Technische Roadmap — daily_revenues Migration

### Kontext
Tagesumsätze werden aktuell als grosser KV-Blob in `app_settings` gespeichert
(Schlüssel `dailyBudgets` / `beaulieu:dailyBudgets`). Als Sofortschutz gegen
Datenverlust wurde `safeUpsertDailyBudgets` eingeführt (liest KV → mergt →
schreibt zurück). Diese Lösung ist stabil, hat aber strukturelle Grenzen:
kein Audit-Log, kein atomarer UPSERT pro Tag, Merge-Konflikte bei Parallelzugriff.

### Zielarchitektur
Normalisierte Tabelle `daily_revenues` in Supabase Postgres:
```sql
-- Vorbereitet in supabase/migrations/20260507_daily_revenues.sql
CREATE TABLE daily_revenues (
  restaurant_id TEXT    NOT NULL,  -- 'oliv' | 'beaulieu'
  date          DATE    NOT NULL,
  actual_revenue        NUMERIC,
  planned_revenue       NUMERIC,
  actual_food           NUMERIC,
  actual_beverage       NUMERIC,
  actual_labor_cost     NUMERIC,
  previous_year_revenue NUMERIC,
  created_at    TIMESTAMPTZ DEFAULT now(),
  updated_at    TIMESTAMPTZ DEFAULT now(),
  updated_by    TEXT,              -- user email für Audit-Trail
  PRIMARY KEY (restaurant_id, date)
);
```
Jeder Tag hat einen eindeutigen Datensatz — kein Blob, kein Merge nötig.

## Gotchas
- **Supabase Migrations:** All SQL migration scripts in `supabase/migrations/` **must** be executed sequentially in the Supabase SQL Editor.
- **Tenant Filtering:** Data for Beaulieu is filtered by `id LIKE 'b-%'` and for Oliv by `id NOT LIKE 'b-%'`; there is no explicit `restaurant_id` column.
- **Mirus Name Mapping:** Manual mapping might be required for Mirus imports to correctly link employee names.
- **Default Budget Seed:** The 2026 budget is seeded automatically upon first load if no `plLineItems` exist for that year.
