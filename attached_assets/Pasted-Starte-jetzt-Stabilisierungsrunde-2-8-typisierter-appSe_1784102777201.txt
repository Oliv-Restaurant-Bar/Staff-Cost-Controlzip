Starte jetzt Stabilisierungsrunde 2.8: typisierter appSettingsTable-Wrapper und gezielte Isolation von supabase as any.

Ziel

Die direkten, untypisierten Zugriffe auf die Supabase-Tabelle für App-/KV-Einstellungen sollen hinter einem kleinen, typisierten Wrapper isoliert werden.

Dabei dürfen keine fachlichen Speicher-, Lade-, Merge-, Konflikt-, Tombstone-, Tenant- oder Offline-Regeln verändert werden.

Diese Runde ist ein reines Typisierungs- und Infrastruktur-Refactoring.

Wichtige Leitplanken

1. Keine fachliche Logik verändern.
2. Keine Datenmigration durchführen.
3. Keine Tabellen, Spalten, Keys oder gespeicherten JSON-Strukturen ändern.
4. Keine bestehenden Merge-Regeln vereinheitlichen.
5. Keine neuen automatischen Schreibvorgänge einführen.
6. Reine Reads dürfen weiterhin niemals Writes auslösen.
7. updatedAt darf nur bei echten Änderungen verändert werden.
8. Bestehende Tenant-Isolation vollständig erhalten.
9. Bestehende Availability-, Retry- und Offline-Regeln nicht verändern.
10. Keine breite Supabase-Abstraktionsschicht für die gesamte App bauen.
11. Kein Repository-Pattern, keine neue Service-Architektur und keine unnötigen Generics einführen.
12. Nur die Tabelle beziehungsweise die Zugriffe kapseln, die aktuell supabase as any benötigen.

T301 – Vollständige Bestandsaufnahme

Suche projektweit nach:

supabase as any

sowie nach ähnlichen Konstrukten:

(supabase as any)
.from("app_settings")
.from('app_settings')
.from("appSettings")

und nach dem tatsächlich verwendeten Tabellennamen.

Lies alle betroffenen Dateien vollständig.

Erstelle vor Änderungen eine kompakte Übersicht:

Datei	Tabelle	Operation	select/insert/update/upsert/delete	Rückgabetyp	Warum aktuell any

Kläre insbesondere:

• tatsächlicher Tabellenname
• Primär- beziehungsweise Konfliktschlüssel
• Tenant-Spalte
• Key-Spalte
• JSON-/Blob-Spalte
• updated_at-Spalte
• optionale oder nullable Felder
• ob unterschiedliche Stellen unterschiedliche Select-Shapes erwarten
• ob das generierte Supabase-Datenbankschema die Tabelle bereits enthält
• ob any nur wegen fehlender DB-Typen oder wegen dynamischer Aufrufe verwendet wird

Keine Annahmen treffen. Die Signaturen aus dem realen Code und den vorhandenen Typen ableiten.

T302 – Kleinsten sinnvollen Wrapper entwerfen

Erstelle einen kleinen, typisierten Wrapper, beispielsweise:

appSettingsTable(...)

oder:

getAppSettingsTable(...)

Die Benennung soll zu den bestehenden Projektkonventionen passen.

Bevorzugte Richtung:

type AppSettingsRow = {
  tenant_id: string;
  key: string;
  value: unknown;
  updated_at: string | null;
};

Die echten Feldnamen müssen aus dem vorhandenen Code übernommen werden.

Der Wrapper darf sinngemäss nur den typisierten Tabellenzugriff bereitstellen:

export function appSettingsTable(client: SupabaseClient) {
  return client.from("app_settings");
}

Falls Supabase aufgrund fehlender generierter Tabellentypen weiterhin lokal gecastet werden muss, dann den Cast genau einmal innerhalb des Wrappers isolieren.

Beispiel:

export function appSettingsTable(client: SupabaseClient) {
  return (client as AppSettingsSupabaseClient).from("app_settings");
}

oder mit einer gezielten Tabellen-/Query-Typisierung.

Kein any an die Aufrufer weiterreichen.

T303 – Typen fachlich korrekt definieren

Definiere nur die tatsächlich benötigten Typen:

export type AppSettingsRow = ...
export type AppSettingsInsert = ...
export type AppSettingsUpdate = ...

Falls Insert und Row identisch sind, keine künstlichen Duplikate erzeugen.

Beachte:

• updated_at kann beim Insert eventuell optional sein
• DB-generierte Felder dürfen nicht zwingend verlangt werden
• JSON-Werte sollen nicht unnötig auf Record<string, unknown> eingeschränkt werden, falls auch Arrays, Strings oder null technisch erlaubt sind
• bestehende Domain-Guards wie asRecordBlob bleiben verantwortlich für die fachliche Shape-Prüfung
• der Tabellenwrapper darf keine Domain-Validierung übernehmen
• keine falsche Sicherheit durch zu enge Typen erzeugen

Wenn ein vorhandener Supabase-Json-Typ existiert, nutze ihn.

T304 – Direkte Zugriffe schrittweise ersetzen

Ersetze nur die direkten supabase as any-Zugriffe auf diese Tabelle.

Vorgehen:

1. Wrapper erstellen.
2. Eine betroffene Datei migrieren.
3. Typecheck beziehungsweise gezielte Tests ausführen.
4. Nächste Datei migrieren.
5. Nach jeder Domain prüfen, dass kein Verhalten verändert wurde.

Nicht gleichzeitig andere Supabase-Tabellen refactoren.

Nicht verändern:

• Reihenfolge von Local- und Remote-Writes
• Read-/Write-Pfade
• Merge-Regeln
• Fehlerbehandlung
• Retry-Verhalten
• Availability-State
• Notifications
• Cache-Invalidierung
• localStorage
• updatedAt
• Tombstones
• Delete-Verhalten
• Return-Werte der öffentlichen Funktionen

T305 – Read-, Write- und Delete-Semantik erhalten

Für jeden migrierten Aufruf verifizieren:

Select:

• gleiche Spalten
• gleiche Filter
• gleiche Tenant-Bedingung
• gleiches .single(), .maybeSingle() oder Listenverhalten
• identische Behandlung von data === null
• identische Behandlung von Supabase-Fehlern

Upsert:

• identischer Payload
• identischer onConflict
• identische Spaltennamen
• identische Return-/Select-Kette
• kein zusätzlicher Write
• kein automatisch gesetztes updatedAt, falls es vorher nicht gesetzt wurde

Delete:

• identische Filter
• identische Tenant-Isolation
• keine breitere Delete-Bedingung
• kein Löschen nur anhand des Keys, wenn vorher zusätzlich Tenant oder User geprüft wurde

T306 – Keine Vermischung mit kv-blob-utils

Der neue appSettingsTable-Wrapper und kv-blob-utils.ts haben unterschiedliche Aufgaben.

appSettingsTable:

• typisierter Supabase-Tabellenzugriff
• Infrastruktur
• kennt Tabellen- und Feldtypen

kv-blob-utils:

• Shape-Guard
• localStorage-Parse-Guard
• Supabase-unabhängig

Nicht zusammenführen.

kv-blob-utils darf weiterhin keinen Supabase-Import erhalten.

T309 – Generated Types prüfen

Prüfe, ob die sauberste Lösung eine Ergänzung der bestehenden Supabase-Datenbanktypen ist.

Falls die Tabelle real existiert, aber in den generierten Typen fehlt:

Option A:

Die vorhandenen lokalen Datenbanktypen gezielt ergänzen, falls diese Datei im Projekt bewusst manuell gepflegt wird.

Option B:

Einen lokalen, eng begrenzten Client-/Tabellentyp für appSettingsTable verwenden, falls die generierten Typen nicht manuell verändert werden sollen.

Keine echte Supabase-Codegenerierung vortäuschen.

Keine automatisch generierte Datei manuell verändern, wenn sie laut Projektkonvention jederzeit überschrieben wird, ausser dies ist im Projekt ausdrücklich der bestehende Prozess.

Begründe die gewählte Variante im Abschlussbericht.
