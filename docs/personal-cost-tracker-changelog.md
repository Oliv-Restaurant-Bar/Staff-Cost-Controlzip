## 2026-09-29, continued — systematic repo-wide sweep for the "false success" bug class

After finding a second instance of the bulk-save bug in the same session (the `handleApplyTemplate`/`setTimeout` closure bug above), the client asked for this to stop being found one at a time. Rather than wait to trip over more instances, ran a dedicated repo-wide audit for the whole bug class — not just the SchedulePlanner file where we'd been finding it.

**Method:** two parallel audits covering every dialog/form component in the app with a save/apply-style callback prop (30 files total, split into `src/components/schedule-planner/*` + `src/components/umsatzabstimmung/*`, and `src/components/produkte/*` + misc others), each tracing the full callback chain from the UI component through to the actual Supabase write to determine whether a success signal (toast, dialog close, cleared draft state) could ever reach the user before — or without — the write being confirmed.

**Findings, and what was actually fixed vs. ruled out:**

- **Genuine bugs found and fixed** (11 call sites across 4 `src/lib` store functions + 2 SchedulePlanner-family files):
  - `src/lib/basiskomponenten-store.ts`'s `saveBasiskomponentenToDB` and `src/lib/rezeptur-store.ts`'s `saveRezepturenToDB` returned `Promise<void>` and swallowed their own errors — by the *rezeptur* one's own doc comment, this was explicitly by design ("existing callers call this fire-and-forget without awaiting"). Both now return `Promise<boolean>`; every caller in `BasiskomponentenManager.tsx` (3 handlers) and `Produkte.tsx`/`RezepturDialog.tsx`/`BulkRezepturUpdate.tsx` now awaits the result and only shows success / closes after a confirmed write, with an explicit error toast otherwise.
  - `src/lib/produkte-store.ts`'s `saveProductGroupsToDB` was local-storage-first (wrote to `localStorage` before attempting Supabase, silently swallowed the error) — the exact anti-pattern this project's own CLAUDE.md flags as a regression. Converted to database-first, now returns `Promise<boolean>`. Its sibling `saveProductCostsToDB` had the same swallowed-error shape; same fix. Callers in `Produkte.tsx` (5 call sites) and `GruppenAnalyse.tsx` (2 call sites) updated to await and gate their UI on the result.
  - `src/lib/import-settings-db.ts`'s `saveImportSettings` never threw even on failure (caught internally, showed its own toast via `notifyKVBackupProblem`, then resolved normally) — meaning its one caller, `ImportCockpitPage.tsx`'s `handleSaveSettings`, had no way to know it failed and closed the dialog + showed its own success toast regardless. Now returns `Promise<boolean>`; the caller gates the close/toast on it and rolls back its optimistic local state on failure.
  - `src/pages/SchedulePlanner.tsx`: 4 more handlers in the same file as the earlier `handleApplyTemplate` fix — `handleSaveDaysOff` (unawaited `upsertEmployee`, unconditional success toast), `handleEmployeeFormSubmit` (same shape, employee edits), `handleActualHoursChange` (fire-and-forget `saveActualHourEntry`, whose `{ok, error}` result was never checked, no failure signal anywhere), and the `_offerDeleteIst` quick-undo action (same). All four now await/check the result and only report success after confirmation. `DaysOffConfigDialog.tsx`'s `onSave` prop and `EmbeddedSchedulePlanner.tsx`'s equivalent `handleSaveDaysOff` updated to match the new `Promise<boolean>` contract.
  - Also removed a redundant *second* unconditional success toast in `handleSaveShiftConfig` (SchedulePlanner.tsx) — `ShiftConfigDialog.tsx` already shows its own after `updateShifts`, so a failure produced two false "success" signals stacked before the real (delayed) error toast from `kvSetConfirmed`.
- **Investigated and ruled out as false positives** — worth recording so this doesn't get "fixed" again by a future pass: `AdyenAbgleichSection.tsx`'s and `TagesabschlussSection.tsx`'s `persist()` helpers were flagged by the audit for having no `try/catch` around their save calls, but `saveAdyenAbstimmung`/`saveTagesabschluss` (`src/lib/adyen-abstimmung-db.ts`, `src/lib/tagesabschluss-db.ts`) already never throw — they catch internally and show a real error+retry toast via `notifyKVBackupProblem` on failure. Not a match for this bug class; left untouched.
- **Confirmed as a genuine gap, but deliberately not fixed this pass** (different shape from the rest, needs a decision rather than a mechanical fix): `PlannedHoursImportButton.tsx`'s `doImport` shows a success toast for a PDF/Excel schedule import that only ever writes to `localStorage` — `importSchedulePDF` (`src/hooks/usePersonnelData.ts`) never reaches Supabase at all. This isn't a race, the feature genuinely has no database persistence. However, the page that uses it (`src/pages/Index.tsx`, routed at `/overview`) is not linked from any nav and is explicitly commented "Legacy" in `App.tsx` — it's reachable only by typing the URL, not part of the flow the client actually uses (that's `SchedulePlanner.tsx`, already fixed). Flagging rather than building out full persistence for an unlinked legacy page; say if this should be prioritized, deleted, or left as-is.
- **Two smaller, different-shaped issues spotted in passing, not fixed (out of scope for this specific bug class):** `ImportConflictDialog.tsx` (used in `Settings.tsx`) triggers its import-apply handler on *every* radio-button click while picking a conflict resolution, not just on the final confirm — a different bug (premature *write*, not a false success signal); and `src/components/personal-fix/OvertimeCostCard.tsx`'s `EmployeeOvertimeModal` has the same false-success shape but has zero importers anywhere in the app — dead code, not reachable, so no user-facing fix needed (candidate for deletion in a cleanup pass).
- **Verified:** `npx tsc --noEmit -p tsconfig.app.json` — zero new errors (diffed against a fresh baseline, not just counted — several pre-existing errors shifted line numbers from the edits but are the same errors). `npx vitest run` — back to the exact 23-failed-file/36-failed-test baseline (one run showed 24/37, re-ran and confirmed flaky, not caused by any of these changes).
